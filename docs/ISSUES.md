# Issue Guide

Use GitHub Issues to report public, reproducible work for Gilbert Codex:

- [Open a bug report](https://github.com/UrbanWafflezz/GilbertCodex/issues/new?template=bug_report.yml) for broken behavior with clear reproduction steps.
- [Share alpha tester feedback](https://github.com/UrbanWafflezz/GilbertCodex/issues/new?template=alpha_tester_feedback.yml) after installing, running from source, or trying a real coding task.
- [Request a feature](https://github.com/UrbanWafflezz/GilbertCodex/issues/new?template=feature_request.yml) when the user problem and acceptance criteria are clear.
- [Report platform support results](https://github.com/UrbanWafflezz/GilbertCodex/issues/new?template=platform_port.yml) for macOS, Linux, Windows packaging, source runs, or native shell behavior.

Do not post provider keys, GitHub tokens, local databases, private workspace contents, private repository names, or sensitive terminal output in public issues. Use the security policy for vulnerabilities or sensitive local-data concerns.

## Useful Issue Details

Good issues usually include:

- the app version or commit SHA
- operating system, CPU architecture, and install method
- the smallest reproduction steps
- expected behavior and actual behavior
- sanitized screenshots, logs, or command output
- whether the issue blocks testing, contribution, or normal use

## Maintainer Triage

Start with GitHub's default labels:

- `bug`
- `documentation`
- `enhancement`
- `good first issue`
- `help wanted`
- `question`

Add narrower area labels once the repository has enough issue volume to justify them. Keep public issues small enough for contributors to pick up, and move security-sensitive details out of public threads.
